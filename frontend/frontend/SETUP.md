# GP-Store Flutter app - setup

## What's built so far

- Full auth flow: register, login (email/password AND mobile OTP), secure
  token storage, automatic refresh-token rotation, logout.
- Real Home screen: search, categories, offers, and product sections backed
  by genuine backend endpoints.
- Product detail, add to cart, and a working cart (quantity steppers, remove).
- **Full checkout**: address management (with real GPS capture via
  geolocator), a live cost preview (subtotal/discount/delivery fee/estimated
  total, computed before committing - not a surprise at the end), coupon
  entry, COD/UPI payment selection, and order confirmation with a real UPI
  deep-link launch via url_launcher.

- **Not built yet**: order history/tracking, profile, wishlist, notifications
  screen. Checkout was the highest-priority remaining piece - a customer can
  now complete a full purchase, which is the actual point of the app.

## New dependencies this round

- `geolocator` - real device GPS for address capture (backend needs real
  coordinates for the deliverability/distance calculation - a full
  interactive map picker is the eventual upgrade, not built yet).
- `url_launcher` - opens the real UPI deep link in whatever UPI app is
  installed (GPay/PhonePe/Paytm).

Both need platform permission setup:
- **Android**: `ACCESS_FINE_LOCATION` permission in `android/app/src/main/AndroidManifest.xml`.
- **iOS**: `NSLocationWhenInUseUsageDescription` in `ios/Runner/Info.plist`.
I haven't added these manifest entries myself - I don't have your actual
Android/iOS project files in front of me (they're generated by `flutter
create`, not something I authored) - add them before testing on a real device.

## Real backend gaps closed this round

- **Checkout preview endpoint** (`GET /api/orders/checkout-preview`) - didn't
  exist before. Without it, a customer would only discover delivery fees
  after already placing the order.
- **Cart quantity decrease/remove** - the backend could only increment
  quantity before; added proper update/remove with ownership checks.
- **A critical bug**: `Cart.items` and `CartItem.cart` had no
  back-reference pair (unlike Product/ProductVariant, which does this
  correctly) - `GET /api/carts/mine` would have infinite-looped and crashed
  the moment any cart had real items in it. Fixed.
- **A related design gap**: since `ProductVariant.product` is hidden from
  JSON (that's what prevents the recursion above), a raw cart response
  couldn't say what product an item even was. Added a proper `CartResponse`
  DTO with real product name/brand included, matching the pattern already
  used for orders and payments.

## Required setup before this runs (I cannot run these myself)

I don't have Flutter/Dart installed in my sandbox, and no network access to
fetch packages - so these steps are genuinely required from you, not
optional cleanup:

1. **Install dependencies:**
   ```
   flutter pub get
   ```

2. **Generate the model code.** `auth_models.dart` uses `freezed` and
   `json_serializable`, which generate `auth_models.freezed.dart` and
   `auth_models.g.dart` at build time - those files don't exist yet and the
   app will NOT compile without running this:
   ```
   dart run build_runner build --delete-conflicting-outputs
   ```
   Re-run this any time you add/change a `@freezed` model.

3. **Point it at your backend.** The API base URL is NOT hardcoded (same
   principle as the backend's env-var config) - pass it at run time:
   ```
   flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8081/v1
   ```
   - `10.0.2.2` is the Android emulator's special alias for your computer's
     own `localhost` - it is NOT a typo, and it only works from the emulator.
   - Testing on a **physical phone**: use your computer's real LAN IP
     instead (e.g. `http://192.168.1.x:8081/v1`), and make sure your phone
     and backend are on the same network.
   - Testing against your **deployed Railway backend**: use that real HTTPS
     URL instead.

4. **Backend must actually be running and reachable** at whatever URL you
   pass in step 3 - via `docker compose up`, a deployed Railway instance, or
   similar. This app has nothing to talk to otherwise.

## Notes

Error messages shown on login/register failure come from the real backend
(`ApiException.message`, unwrapped from the Dio exception) - not a generic
Dart exception string. If the backend rejects a login with "Invalid email
or password", that's exactly what the user sees.
