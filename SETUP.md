# GP-Store Flutter app - setup

## What's built so far

- Full auth flow: register, login (email/password AND mobile OTP), secure
  token storage, automatic refresh-token rotation, logout.
- Real Home screen: search, categories, offers, and product sections backed
  by genuine backend endpoints.
- Product detail, add to cart, and a working cart (quantity steppers, remove).
- **Full checkout**: address management (with real GPS capture via
  geolocator), a live cost preview (subtotal/discount/delivery fee/estimated
  total, computed before committing - not a surprise at the end), coupon
  entry, COD/UPI payment selection, and order confirmation with a real UPI
  deep-link launch via url_launcher.

- **Not built yet**: order history/tracking, profile, wishlist, notifications
  screen. Checkout was the highest-priority remaining piece - a customer can
  now complete a full purchase, which is the actual point of the app.

## New dependencies this round

- `geolocator` - real device GPS for address capture (backend needs real
  coordinates for the deliverability/distance calculation - a full
  interactive map picker is the eventual upgrade, not built yet).
- `url_launcher` - opens the real UPI deep link in whatever UPI app is
  installed (GPay/PhonePe/Paytm).

Both need platform permission setup:
- **Android**: `ACCESS_FINE_LOCATION` permission in `android/app/src/main/AndroidManifest.xml`.
- **iOS**: `NSLocationWhenInUseUsageDescription` in `ios/Runner/Info.plist`.
I haven't added these manifest entries myself - I don't have your actual
Android/iOS project files in front of me (they're generated by `flutter
create`, not something I authored) - add them before testing on a real device.

## Real backend gaps closed this round

- **Checkout preview endpoint** (`GET /api/orders/checkout-preview`) - didn't
  exist before. Without it, a customer would only discover delivery fees
  after already placing the order.
- **Cart quantity decrease/remove** - the backend could only increment
  quantity before; added proper update/remove with ownership checks.
- **A critical bug**: `Cart.items` and `CartItem.cart` had no
  back-reference pair (unlike Product/ProductVariant, which does this
  correctly) - `GET /api/carts/mine` would have infinite-looped and crashed
  the moment any cart had real items in it. Fixed.
- **A related design gap**: since `ProductVariant.product` is hidden from
  JSON (that's what prevents the recursion above), a raw cart response
  couldn't say what product an item even was. Added a proper `CartResponse`
  DTO with real product name/brand included, matching the pattern already
  used for orders and payments.

## Required setup before this runs (I cannot run these myself)

I don't have Flutter/Dart installed in my sandbox, and no network access to
fetch packages - so these steps are genuinely required from you, not
optional cleanup:

1. **Install dependencies:**
   ```
   flutter pub get
   ```

2. **Generate the model code.** `auth_models.dart` uses `freezed` and
   `json_serializable`, which generate `auth_models.freezed.dart` and
   `auth_models.g.dart` at build time - those files don't exist yet and the
   app will NOT compile without running this:
   ```
   dart run build_runner build --delete-conflicting-outputs
   ```
   Re-run this any time you add/change a `@freezed` model.

3. **Point it at your backend.** The API base URL is NOT hardcoded (same
   principle as the backend's env-var config) - pass it at run time:
   ```
   flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8081/v1
   ```
   - `10.0.2.2` is the Android emulator's special alias for your computer's
     own `localhost` - it is NOT a typo, and it only works from the emulator.
   - Testing on a **physical phone**: use your computer's real LAN IP
     instead (e.g. `http://192.168.1.x:8081/v1`), and make sure your phone
     and backend are on the same network.
   - Testing against your **deployed production API**: use that real HTTPS
     URL instead (for example `https://api.gpstore.co.in/v1`).

4. **Backend must actually be running and reachable** at whatever URL you
   pass in step 3 - via `docker compose up`, the Hostinger VPS, or
   similar. This app has nothing to talk to otherwise.

## Platform folders (android/, web/) - what's real and what needs one more step

### Android - ready to build, with two small one-time gaps

The `android/` folder is complete and correct - Gradle scripts, manifest with
the real permissions this app needs (internet, location for GPS address
capture), `MainActivity`, themes, and a basic launcher icon. Two things I
genuinely cannot generate myself, both quick to resolve:

1. **Gradle wrapper JAR** (`android/gradle/wrapper/gradle-wrapper.jar`) is a
   compiled binary file - I can only write text files. The `gradle-wrapper.properties`
   (which tells Gradle which version to fetch) is already there and correct.
   Fix: either open the project in Android Studio once (it regenerates the
   wrapper automatically), or if you have Gradle installed anywhere, run
   `gradle wrapper --gradle-version 8.6` inside `android/`. Either is a
   one-time step.

2. **The launcher icon is a basic placeholder** - a simple vector shape
   (green diamond, white bag), not a real logo, since I can only write text
   files and PNGs are binary. It's completely valid and will build fine.
   When you have a real logo, the standard tool for this is the
   `flutter_launcher_icons` package - point it at one source image and it
   generates every required size automatically.

3. **`android/local.properties`** doesn't exist yet either - this is
   normal and expected. The Flutter CLI creates it automatically, pointing
   at your installed Flutter SDK, the first time you run `flutter run` or
   `flutter build apk` in this project. You don't need to create it by hand.

**Build the APK:**
```
flutter build apk --release
```
Output lands at `build/app/outputs/flutter-apk/app-release.apk`. Note the
`android/app/build.gradle` signing config currently falls back to debug
signing so this command succeeds out of the box for testing - replace it
with a real release keystore before publishing to the Play Store, or Google
will reject the upload.

### Web - fully ready to build, nothing missing

Unlike Android's icon, I could write real, valid SVG icons for web (SVG is
a text format, not binary) - so `web/` has no placeholder gaps at all.

**Build for web:**
```
flutter build web --release
```
Output lands in `build/web/` - deploy that folder's contents to any static
host (Netlify, Vercel, GitHub Pages, etc.).

### iOS, macOS, Windows, Linux - deliberately not hand-written here

These weren't skipped by oversight. iOS and macOS project files
(`.pbxproj` in particular) are Xcode's own generated format - not simple
text templates but a specific structure Xcode itself maintains, where a
single wrong byte can make Xcode refuse to even open the project, often
with no useful error message. Windows' Visual Studio project files have a
similar risk profile. Hand-authoring these convincingly is genuinely unsafe,
not just tedious.

The correct, safe way to add them: once you have the Flutter SDK installed
on any machine (yours, a CI runner, whatever), run this once from the
project root - it's a supported, standard Flutter CLI operation designed
specifically for adding platforms to an *existing* project, and it will
**not** touch `lib/`, `test/`, `android/`, or `web/`:
```
flutter create --platforms=ios,macos,windows,linux .
```
This generates all four correctly, matching whatever Flutter/Xcode/Visual
Studio versions you actually have - which is also safer than me guessing
version numbers that might not match your toolchain at all.

## Getting an APK or a live browser link without installing Flutter yourself

I can't build or run Flutter in my own sandbox - no SDK installed, no
network access to even download one. `.github/workflows/build-and-deploy.yml`
is the actual answer to that: GitHub's own free infrastructure builds this
project for you.

**One-time setup, after pushing this project to a GitHub repo:**
1. Repo Settings -> Pages -> Source -> select **"GitHub Actions"** (one click - without this, there's nothing for the workflow to deploy to).
2. Push to `main` (or use the "Run workflow" button under the Actions tab if you don't want to make a commit).

**A critical caveat, not a minor detail:** both the APK and the web build
will install/load and show the app's UI regardless - but every single API
call (login, browsing products, everything) will fail until they know
where your real backend actually lives. The app's own coded default
(`10.0.2.2`, the Android *emulator's* localhost alias) is unreachable from
both a real phone and a public website. Once your backend is deployed
somewhere reachable (e.g. the Hostinger VPS, per [PRODUCTION_CHECKLIST.md](PRODUCTION_CHECKLIST.md)
and `backend/DEPLOYMENT.md`),
set it once: this repo's Settings -> Secrets and variables -> Actions ->
Variables tab -> New repository variable -> name `API_BASE_URL`, value
your backend's real URL with `/v1` on the end. Every build after that
picks it up automatically.

**What you get, both automatically, on every push to `main`:**
- A downloadable customer+admin APK - open the finished Actions run, look under **Artifacts**, download `gpstore-customer-admin-arm64.apk`, install it on an Android phone (you'll need to allow "install from unknown sources" since it isn't signed for the Play Store yet). GitHub's artifact zip size is not the APK size.
- A live, clickable web version at `https://<your-github-username>.github.io/<repo-name>/` - opens directly in any browser, no download needed.

Every push after the first one rebuilds and redeploys automatically - you
never need to repeat these steps.

## Notes

Error messages shown on login/register failure come from the real backend
(`ApiException.message`, unwrapped from the Dio exception) - not a generic
Dart exception string. If the backend rejects a login with "Invalid email
or password", that's exactly what the user sees.
