# Slice 12 — connecting the Flutter apps to the marketplace

## What could and could not be verified

**There is no Flutter SDK in the build container.** `which flutter dart` finds
nothing. `flutter analyze`, `flutter test` and `dart run build_runner` cannot be
executed here at all, and the repo's `.freezed.dart` / `.g.dart` part files are
gitignored and generated by CI — so no Dart in this repository compiles locally
even in principle.

The CI job that *can* do it (`flutter-checks`, Flutter 3.35.7: `pub get` →
`build_runner build` → `analyze --no-fatal-infos` → `flutter test`) runs only on
push or PR to `main`, and this slice opened neither.

So, precisely:

| | status |
|---|---|
| Backend changes | **executed** — full suite, SpotBugs, in this container |
| Backend contract tests for the new fields | **executed** |
| Dart source | **written; not compiled, not analyzed, not run** |
| Dart tests | **written; not run** |
| Dart structure (braces, imports, part-file naming) | **statically checked** by script |
| Dart→API route agreement | **executed**, as a backend test |
| Dart↔backend field names | **statically checked** by script |

Nothing here should be read as "the frontend is tested". It is not.

## The two contract gaps that had to be closed first

The apps were asked to group a basket by shop and label an order with its
seller. Neither was possible, because neither fact was in the response:

- `CartResponse.CartItemResponse` carried no `shopId`;
- `OrderResponse` carried no shop at all.

A client wanting to group had two options — fetch something else and guess, or
invent a grouping the server never decided. Both put marketplace logic in Dart,
which is the thing this transformation exists to prevent. So the fields were
added to the contract instead, and pinned by tests that run here.

Both are additive (§96): every key an existing client reads is still present,
asserted by name, so the released app on a customer's phone is unaffected (§12).

**The cost is tied to the deployment, not the basket.** Shop names are looked up
only under a marketplace. Under one shop nothing displays a name, so the cart
read costs exactly what it did before — which `CheckoutPerformanceTest` enforces,
and which caught the first version of this doing one lookup per shop.

## What was built in Dart

**Shared core** — `lib/core/marketplace/`: `Storefront` / `MarketplaceMode`
models, a repository over `/api/marketplace/**`, and `ShopContext`.

`ShopContext` holds a *preference*, not an authorization, and the comment on it
says so at length. The `X-Shop-Id` header it produces can only NARROW a scope
the credential already permits; the server refuses a shop the caller is not
entitled to rather than honouring it. Nothing in Dart validates it, deliberately
— a second, weaker copy of a server rule is wrong the first time the two
disagree.

**Customer** — `cart_grouping.dart` (a pure function over what the server already
decided), cart model fields, `OrderGroupRepository` + models over
`/api/orders/groups`, and the seller on `OrderSummary`.

**Merchant** — `ShopSelfServiceRepository` over `/api/shop/profile|readiness|earnings|open-work`.
No route here takes a shop id, which is the security design rather than an
omission: every call acts on the shop the credential resolved to, so there is no
id for a caller to change.

**Platform admin** — `PlatformRepository` over `/api/platform/**`.

**Error handling** — nothing was duplicated. The backend's own message already
wins in `extractErrorMessage`, so "This shop is not currently taking orders",
"…is currently unavailable" and the rest surface verbatim. What was missing was
a way to *branch*, so `meansShopViewIsStale` was added: 404/409/403 mean reload,
401 does not (that is a dead session, and reloading will not fix it).

## The one screen changed, and why only one

`cart_screen.dart` groups by shop **only when `isSplitAcrossShops` is true**. A
basket from one shop — every basket in this deployment today — takes the
original branch: the same `ListView`, the same tiles, no headers, no mention of
shops. §2: an existing customer must not have to learn that a multi-shop
architecture exists.

Every other screen was left alone on purpose. An edit to a screen I cannot
compile, cannot analyze and cannot run is an unverified change to software real
customers are using today. The data layer is additive — nothing existing imports
it, so it cannot alter any current behaviour — which is why it was safe to write
and the screens were not.

Each of these needs a person with a Flutter SDK, and each consumes a layer that
now exists.

### Worker

**No isolation work is needed.** A rider's shop comes from their roster row
server-side (Slice 9), so a worker from Shop A cannot see Shop B's jobs
regardless of what the app does. What is missing is only *display*: showing the
rider which shop they are working for.

### Platform admin

New screens over `PlatformRepository`: merchant applications and
approval/rejection with reasons, shops and suspension, and the marketplace
overview. Gated server-side on `PERM_PLATFORM_ADMIN`, which no shop role holds.

## Not done, deliberately

**No commission arithmetic anywhere.** W2 is undecided. `ShopEarnings` has no fee
field, and a zero-valued one beside real money would look like a decision that
has been made.

**No 25% pricing rule in Flutter, and no ranking or eligibility logic.** All of
it stays server-side.
